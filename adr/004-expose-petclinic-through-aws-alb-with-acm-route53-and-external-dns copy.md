# ADR-004: Expose Petclinic through AWS ALB with ACM, Route 53 and ExternalDNS

## Status

Accepted

---

## Context

The Petclinic application runs on an Amazon EKS cluster and is deployed using Kubernetes.

The application is exposed externally through an AWS Application Load Balancer.

The AWS Application Load Balancer is created and managed by the AWS Load Balancer Controller based on a Kubernetes Ingress resource.

The application also uses Argo Rollouts for progressive delivery.

Therefore, the ALB is not only responsible for exposing the application to the Internet.

It is also used as the traffic management layer for canary deployments.

The resulting architecture needs to support:

- stable public application URL
- HTTPS
- automatic DNS management
- automatic ALB lifecycle management
- progressive traffic shifting
- infrastructure recreation
- declarative configuration
- GitOps-based management

Initially, the application was accessible using the AWS-generated ALB hostname.

Example:

    k8s-petclini-petclini-f0c0d5edee-990875608.eu-central-1.elb.amazonaws.com

This works technically, but it is not suitable as the stable public identity of the application.

The AWS-generated hostname is infrastructure-specific.

It may change when the ALB is destroyed and recreated.

This is especially relevant because the environment is designed to support infrastructure recreation using:

    terraform destroy
    terraform apply

After recreation, AWS can create a new ALB with a different hostname.

The application therefore requires a stable DNS name that is independent of the lifecycle of the underlying AWS infrastructure.

The desired public endpoint is:

    https://petclinic.website

The expected architecture is:

    Internet
        |
        v
    Route 53
        |
        v
    AWS Application Load Balancer
        |
        v
    Kubernetes Ingress
        |
        v
    Argo Rollouts
        |
        +-- Stable Service
        |
        +-- Canary Service
        |
        v
    Petclinic Pods

The infrastructure should also tolerate the following lifecycle:

    Terraform destroy
        |
        v
    ALB disappears
        |
        v
    Terraform apply
        |
        v
    New ALB is created
        |
        v
    ExternalDNS detects new ALB
        |
        v
    Route 53 record is updated
        |
        v
    petclinic.website points to new ALB

The public application URL should remain unchanged throughout this lifecycle.

---

## Decision

Expose Petclinic using the following architecture:

    Custom domain:
    petclinic.website

    DNS:
    Amazon Route 53

    TLS:
    AWS Certificate Manager

    Load Balancer:
    AWS Application Load Balancer

    Kubernetes integration:
    AWS Load Balancer Controller

    DNS automation:
    ExternalDNS

    Progressive delivery:
    Argo Rollouts

The Kubernetes Ingress is handled by the AWS Load Balancer Controller using:

    ingressClassName: alb

The resulting architecture is:

    Internet
        |
        | HTTPS :443
        v
    Route 53
        |
        | Alias A
        v
    AWS Application Load Balancer
        |
        | HTTPS termination
        v
    Kubernetes Ingress
        |
        v
    Argo Rollouts
        |
        +-------------------+
        |                   |
        v                   v
    Stable Service     Canary Service
        |                   |
        +---------+---------+
                  |
                  v
            Petclinic Pods

ExternalDNS manages the relationship between the Kubernetes Ingress and Route 53.

ACM provides the TLS certificate used by the ALB.

Argo Rollouts controls traffic distribution between stable and canary services.

Terraform remains responsible for AWS infrastructure.

Kubernetes and Helm remain responsible for application-facing configuration.

---

## Why a Custom Domain Was Introduced

Using the AWS-generated ALB hostname directly couples the application URL to an AWS infrastructure resource.

For example:

    k8s-petclini-petclini-f0c0d5edee-990875608.eu-central-1.elb.amazonaws.com

The hostname is generated by AWS.

If the ALB is destroyed and recreated, AWS may assign a different hostname.

This creates a problem for a public application because the application URL would depend on the lifecycle of the infrastructure.

The environment intentionally supports:

    terraform destroy
    terraform apply

Therefore the application should not depend on the generated ALB hostname.

A stable custom domain was introduced:

    petclinic.website

The domain becomes the stable public identity of the application.

The ALB becomes an implementation detail.

The architecture therefore separates:

    Application Identity
            !=
    Infrastructure Identity

The application identity remains stable while the underlying AWS infrastructure can be replaced.

Users always access:

    https://petclinic.website

regardless of which specific ALB currently exists.

---

## Route 53

Amazon Route 53 is used as the authoritative DNS provider for:

    petclinic.website

The domain remains registered at CyberFolks.

Only the DNS authority was delegated to Route 53.

The domain delegation was changed from the CyberFolks nameservers:

    dns1.tld.pl
    dns2.tld.pl
    dns3.tld.pl

to the Route 53 nameservers:

    ns-1272.awsdns-31.org
    ns-382.awsdns-47.com
    ns-796.awsdns-35.net
    ns-1897.awsdns-45.co.uk

This creates a separation between domain registration and DNS management.

Conceptually:

    CyberFolks
        |
        | Domain registration
        v
    petclinic.website

    Route 53
        |
        | DNS authority
        v
    A / Alias / CNAME / TXT records

The domain can therefore remain registered at CyberFolks while AWS-based infrastructure manages the DNS records.

---

## Why Route 53 Was Introduced

The Kubernetes cluster creates and destroys AWS ALBs dynamically.

The ALB hostname is therefore dynamic.

For example:

    ALB #1
        |
        v
    petclinic.website
        |
        v
    ALB #1 hostname

After:

    terraform destroy
    terraform apply

the old ALB may no longer exist.

A new ALB is created:

    ALB #2

The DNS record must then point to the new ALB.

Without automation, this would require:

    Human
        |
        v
    Route 53
        |
        v
    Update DNS record
        |
        v
    New ALB

This introduces unnecessary operational work and creates the possibility of stale DNS records.

Route 53 is therefore used together with ExternalDNS to automate this relationship.

The intended architecture is:

    Kubernetes Ingress
        |
        v
    ExternalDNS
        |
        v
    Route 53
        |
        v
    Current AWS ALB

---

## AWS Certificate Manager

The application is exposed through:

    https://petclinic.website

The AWS ALB therefore requires a TLS certificate matching the public hostname.

AWS Certificate Manager is used to provide this certificate.

The certificate covers:

    petclinic.website

and:

    *.petclinic.website

The certificate is DNS-validated.

The DNS validation creates a CNAME similar to:

    _24879585331d2bf7b66e10b32ea06ddb.petclinic.website

with:

    CNAME

pointing to:

    _e91092096c010c8338364234d7c46255.wzccmgtwzk.acm-validations.aws

After successful DNS validation, ACM issues the certificate.

---

## Why DNS Validation Was Used

DNS validation proves control over the domain without requiring changes to the application servers.

It is also well suited to AWS-managed infrastructure.

The ACM certificate is independent of the ALB lifecycle.

Therefore:

    ACM Certificate
        |
        +-- ALB #1
        |
        +-- ALB #2
        |
        +-- ALB #3

The same certificate can be associated with a newly created ALB after infrastructure recreation.

The certificate therefore provides a reusable TLS identity while the ALB itself remains replaceable.

---

## ACM Certificate and Kubernetes Ingress

The ACM certificate is referenced from the Kubernetes Ingress.

The Ingress contains:

    alb.ingress.kubernetes.io/certificate-arn: arn:aws:acm:eu-central-1:066496973881:certificate/...

This tells the AWS Load Balancer Controller which ACM certificate should be associated with the ALB.

The certificate is therefore part of the declarative Kubernetes networking configuration.

The architecture is:

    Git / Helm
        |
        v
    Kubernetes Ingress
        |
        v
    AWS Load Balancer Controller
        |
        +-- AWS ALB
        |
        +-- ACM Certificate

The ALB configuration can therefore be recreated without manually configuring the certificate through the AWS console.

---

## HTTP and HTTPS Listeners

The Ingress configures both HTTP and HTTPS listeners.

The configuration is:

    alb.ingress.kubernetes.io/listen-ports: '[{"HTTP":80},{"HTTPS":443}]'

This creates:

    HTTP :80
    HTTPS :443

HTTP is not used to serve the application directly.

The Ingress also configures:

    alb.ingress.kubernetes.io/ssl-redirect: "443"

Therefore the request flow is:

    http://petclinic.website
        |
        v
    HTTP :80
        |
        v
    HTTP 301
        |
        v
    https://petclinic.website
        |
        v
    HTTPS :443
        |
        v
    Petclinic

This provides a simple user experience while ensuring that application traffic uses HTTPS.

---

## Target Type

The ALB uses:

    alb.ingress.kubernetes.io/target-type: ip

This configures the ALB to target Kubernetes Pods directly using their IP addresses.

Conceptually:

    AWS ALB
        |
        +--> Pod IP
        |
        +--> Pod IP
        |
        +--> Pod IP

Instead of:

    AWS ALB
        |
        v
    Kubernetes Node
        |
        v
    Kubernetes Service
        |
        v
    Pod

The IP target model is well suited to EKS networking with the AWS VPC CNI because Pods receive VPC-routable IP addresses.

It also reduces unnecessary network hops between the ALB and the application workload.

---

## Kubernetes Ingress Hostname

The Kubernetes Ingress contains the public application hostname:

    host: petclinic.website

This establishes the relationship between the Kubernetes application and the public DNS name.

The same hostname is also used by ExternalDNS.

The Ingress therefore contains:

    external-dns.alpha.kubernetes.io/hostname: petclinic.website

This creates a consistent relationship:

    Kubernetes Ingress
        |
        | host: petclinic.website
        |
        v
    ExternalDNS
        |
        | petclinic.website
        |
        v
    Route 53

The public hostname therefore exists consistently at both the Kubernetes and DNS layers.

---

## ExternalDNS

ExternalDNS is used to automatically synchronize Kubernetes resources with Route 53 DNS records.

Without ExternalDNS, creating an AWS ALB does not automatically update the public DNS record.

The ALB hostname is dynamic.

For example:

    First deployment:

    ALB #1
        |
        v
    k8s-...-1345385844...

    Route 53:

    petclinic.website
        |
        v
    ALB #1

After infrastructure recreation:

    Second deployment:

    ALB #2
        |
        v
    k8s-...-990875608...

The Route 53 record must now point to ALB #2.

ExternalDNS automates this process.

The intended architecture is:

    Kubernetes Ingress
        |
        v
    ExternalDNS
        |
        v
    Route 53
        |
        v
    Current ALB

---

## ExternalDNS Configuration

ExternalDNS is configured with:

    --source=ingress
    --provider=aws
    --domain-filter=petclinic.website
    --aws-zone-type=public
    --ingress-class=alb

This configuration limits ExternalDNS to the required scope.

It watches:

    Kubernetes Ingress

It uses:

    AWS Route 53

It manages records under:

    petclinic.website

It only processes the intended ALB Ingress class.

This reduces the risk of ExternalDNS modifying unrelated DNS records.

---

## ExternalDNS Hostname Annotation

The Kubernetes Ingress contains:

    external-dns.alpha.kubernetes.io/hostname: petclinic.website

This explicitly tells ExternalDNS which hostname it should manage.

The annotation creates a direct relationship between:

    Kubernetes Ingress
            |
            v
    petclinic.website

and:

    Route 53
            |
            v
    petclinic.website

This makes the intended DNS ownership explicit and keeps the configuration declarative.

---

## ExternalDNS TXT Registry

ExternalDNS is configured with:

    --registry=txt
    --txt-owner-id=petclinic-eks

The TXT registry provides ownership tracking for DNS records.

This is important because a Route 53 hosted zone may contain records that are not managed by ExternalDNS.

The TXT registry allows ExternalDNS to distinguish records under its ownership from unrelated DNS records.

Conceptually:

    Route 53
        |
        +-- A / Alias
        |      |
        |      +-- petclinic.website -> ALB
        |
        +-- TXT
               |
               +-- ExternalDNS ownership metadata

The ownership information helps ExternalDNS determine which records it is responsible for managing.

Once ExternalDNS manages the application DNS record, the record should no longer be manually maintained.

---

## Migration from Manually Managed DNS

During the migration to ExternalDNS, the Route 53 hosted zone contained an old manually created Alias record.

The old record pointed to:

    ...1345385844...

The corresponding ALB had already been destroyed and replaced.

The current ALB hostname was:

    ...990875608...

Therefore the existing DNS record was stale.

The stale manual record was removed.

ExternalDNS then created the correct record:

    petclinic.website
        |
        | A / Alias
        v
    ...990875608...

This demonstrated the intended ownership model.

Before:

    Human
        |
        v
    Route 53 A / Alias record
        |
        v
    ALB

After:

    Kubernetes Ingress
        |
        v
    ExternalDNS
        |
        v
    Route 53
        |
        v
    Current ALB

The DNS lifecycle is therefore controlled by the Kubernetes resource rather than manual AWS console changes.

---

## Route 53 Alias Record

The final DNS record is an A record using an Alias target.

Conceptually:

    petclinic.website
        |
        | A / Alias
        v
    AWS ALB

The target is the current ALB hostname:

    dualstack.k8s-petclini-petclini-f0c0d5edee-990875608.eu-central-1.elb.amazonaws.com

An Alias record is appropriate for an AWS ALB.

It allows Route 53 to reference the AWS load balancer directly without storing its underlying IP addresses.

This is important because an ALB does not provide a permanent public IP address that should be hard-coded into DNS.

The correct abstraction is:

    DNS
        |
        v
    AWS ALB

rather than:

    DNS
        |
        v
    Hard-coded IP address

The Alias record therefore allows the infrastructure to remain dynamic while the application hostname remains stable.

---

## Infrastructure Replacement

A major requirement is that the infrastructure can be destroyed and recreated.

For example:

    terraform destroy
        |
        v
    Old ALB removed
        |
        v
    terraform apply
        |
        v
    New ALB created
        |
        v
    Kubernetes Ingress reconciled
        |
        v
    New ALB hostname
        |
        v
    ExternalDNS
        |
        v
    Route 53 Alias updated
        |
        v
    petclinic.website
        |
        v
    New ALB

The public URL remains:

    https://petclinic.website

The ALB hostname may change.

The DNS record follows the current ALB automatically.

The ACM certificate remains reusable.

Argo Rollouts continues to use the ALB as the traffic management layer.

This provides infrastructure replaceability without changing the application URL.

## Terraform Responsibility

Terraform is responsible for AWS infrastructure and AWS-side resources.

The Terraform layer manages resources such as:

    Route 53
    ACM
    AWS networking
    EKS
    IAM
    AWS Load Balancer Controller IAM resources

Terraform creates the AWS infrastructure required by the platform.

Terraform does not manually manage the application ALB lifecycle.

The ALB is created dynamically by the AWS Load Balancer Controller from Kubernetes resources.

---

## Kubernetes and Helm Responsibility

Kubernetes and Helm are responsible for application-facing configuration.

This includes:

    Deployment / Rollout
    Services
    Ingress
    ServiceAccount
    Application configuration

The Ingress contains the information required to create the desired ALB configuration.

For example:

    ingressClassName: alb

    host:
    petclinic.website

    certificate ARN

    listener configuration

    target type

    SSL redirect

The Kubernetes configuration therefore remains the source of truth for application-facing networking.

---

## AWS Load Balancer Controller Responsibility

The AWS Load Balancer Controller bridges Kubernetes and AWS Elastic Load Balancing.

It watches the Kubernetes Ingress and reconciles the desired state with AWS.

Conceptually:

    Kubernetes Ingress
        |
        v
    AWS Load Balancer Controller
        |
        v
    AWS Application Load Balancer

The controller manages:

    ALB
    listeners
    listener rules
    target groups
    security groups
    target registration

The ALB is therefore dynamically created and updated according to Kubernetes configuration.

---

## ExternalDNS Responsibility

ExternalDNS manages the DNS lifecycle.

Its responsibility is:

    Kubernetes Ingress
        |
        v
    ExternalDNS
        |
        v
    Route 53

ExternalDNS should manage:

    petclinic.website

and point it to the current ALB.

It should not be necessary for an operator to manually update the application DNS record after an ALB replacement.

---

## ACM Responsibility

ACM provides the TLS identity for:

    petclinic.website

The certificate remains independent of the ALB lifecycle.

The relationship is:

    ACM Certificate
        |
        v
    AWS ALB :443

The certificate is referenced from the Kubernetes Ingress by ARN.

When the ALB is recreated, the same certificate can be associated with the new ALB.

---

## DNS Delegation

The domain registrar remains CyberFolks.

The authoritative DNS provider is Route 53.

This creates the following responsibility split:

    CyberFolks
        |
        +-- Domain registration

    Route 53
        |
        +-- DNS authority
        +-- A / Alias records
        +-- TXT ownership records
        +-- ACM validation records

The domain ownership is therefore independent from the DNS provider.

Changing the authoritative nameservers does not transfer the domain registration.

It only delegates DNS management to Route 53.

## Verification

The final configuration was verified using several independent checks.

### DNS Delegation

The domain was confirmed to use the Route 53 nameservers:

    ns-1272.awsdns-31.org
    ns-1897.awsdns-45.co.uk
    ns-382.awsdns-47.com
    ns-796.awsdns-35.net

### DNS Resolution

The public DNS record was verified using:

    dig +short petclinic.website

The domain resolves to public IP addresses associated with the ALB infrastructure.

### HTTP Redirect

HTTP was verified using:

    curl -I http://petclinic.website

The response was:

    HTTP/1.1 301 Moved Permanently

with:

    Location: https://petclinic.website:443/

This confirms that HTTP traffic is redirected to HTTPS.

### HTTPS

HTTPS was verified using:

    curl -I https://petclinic.website

The response was:

    HTTP/2 200

This confirms that the application is accessible through HTTPS.

### ALB Listeners

The ALB was verified to have:

    HTTP :80
    HTTPS :443

The HTTP listener redirects traffic to HTTPS.

### Route 53 Alias

The final Route 53 record was verified to point to the current ALB:

    petclinic.website
        |
        | A / Alias
        v
    k8s-petclini-petclini-f0c0d5edee-990875608.eu-central-1.elb.amazonaws.com

This confirmed that DNS follows the currently existing ALB rather than the previously destroyed ALB.

## Alternatives Considered

### Keep Using the AWS ALB Hostname

Rejected.

The AWS-generated hostname is infrastructure-specific.

It can change when the ALB is destroyed and recreated.

It is not suitable as a stable application URL.

It also makes TLS and DNS management less convenient.

The public application should use a stable domain instead.

---

### Manually Manage Route 53 Records

Rejected.

Manual management would require updating:

    petclinic.website
        |
        v
    New ALB

after every ALB replacement.

This creates unnecessary operational work and introduces a risk of stale DNS records.

ExternalDNS provides the required automation.

---

### Keep CyberFolks as the Authoritative DNS Provider

Rejected.

CyberFolks can manage DNS records, but the desired architecture integrates DNS management with AWS and Kubernetes infrastructure.

Route 53 provides direct integration with AWS-based infrastructure and ExternalDNS.

The domain remains registered at CyberFolks.

Only DNS authority is delegated to Route 53.

---

### Use an Elastic IP in Front of the ALB

Rejected.

ALBs are not designed to be addressed using manually managed static IP addresses.

The correct abstraction for an ALB is an AWS DNS target.

Route 53 Alias records provide the native AWS mechanism for pointing a stable domain to an ALB.

---

### Manually Configure the ALB in AWS

Rejected.

Manual ALB configuration would create configuration drift between AWS and Kubernetes.

The desired state should remain declarative and reproducible.

The Kubernetes Ingress should remain the source of truth for application-facing ALB configuration.

---

### Use a Separate Ingress Controller

Rejected.

The AWS Load Balancer Controller already provides the required Kubernetes-to-AWS integration.

A separate ingress controller would introduce additional components and another network layer.

The selected architecture directly connects the AWS ALB with Kubernetes application services.

---

## Consequences

### Positive

- The application has a stable public URL.
- The public URL does not depend on the ALB hostname.
- The ALB can be destroyed and recreated without changing the application URL.
- Route 53 provides authoritative DNS management.
- ExternalDNS automatically updates DNS when the ALB changes.
- ACM provides reusable TLS identity.
- HTTPS is enforced through HTTP-to-HTTPS redirection.
- The ALB is managed declaratively through Kubernetes.
- The ALB configuration is reproducible.
- Argo Rollouts can use the ALB for progressive traffic shifting.
- Stable and canary services can receive controlled traffic percentages.
- Terraform remains responsible for AWS infrastructure.
- Kubernetes remains responsible for application-facing networking.
- ExternalDNS remains responsible for DNS synchronization.
- ACM remains responsible for TLS certificates.
- The infrastructure can be recreated without requiring a manual DNS update.
- The application does not depend on AWS-generated infrastructure hostnames.
- Route 53 Alias records avoid hard-coding ALB IP addresses.
- The architecture provides clear ownership boundaries between components.

### Negative

- The architecture introduces additional AWS and Kubernetes components.
- The platform depends on ExternalDNS for automatic DNS synchronization.
- ExternalDNS requires permissions to read and modify Route 53 records.
- Route 53 becomes an additional AWS-managed dependency.
- ACM introduces another lifecycle that must be maintained.
- ALB provisioning is asynchronous.
- DNS changes are not necessarily visible everywhere immediately.
- The architecture is more complex than directly exposing a Kubernetes Service.
- ALB behavior depends on correct Kubernetes Ingress configuration.
- Argo Rollouts adds additional traffic-management complexity.
- AWS-specific integrations create some vendor coupling.

---

## Operational Rules

The following rules should be followed after introducing this architecture.

### Rule 1 — Do Not Manually Modify the Application DNS Record

Once ExternalDNS manages:

    petclinic.website

the corresponding Route 53 A / Alias record should not be manually maintained.

---

### Rule 2 — Do Not Hard-Code the ALB Hostname

The ALB hostname is dynamic.

Application configuration should use:

    https://petclinic.website

and not:

    k8s-....elb.amazonaws.com

---

### Rule 3 — Keep the ACM Certificate Independent from the ALB Lifecycle

The certificate should remain managed by ACM.

The Kubernetes Ingress should reference the certificate using its ARN.

---

### Rule 4 — Keep DNS Ownership with ExternalDNS

The Kubernetes Ingress should contain:

    external-dns.alpha.kubernetes.io/hostname: petclinic.website

ExternalDNS should remain responsible for synchronizing this hostname with Route 53.

---

### Rule 5 — Route 53 Should Remain the Authoritative DNS Provider

The domain registrar can remain CyberFolks.

The authoritative DNS servers should continue to point to Route 53.

---

### Rule 6 — Infrastructure Recreation Must Not Require Manual DNS Updates

The system should tolerate:

    terraform destroy
    terraform apply

without requiring an operator to manually update:

    petclinic.website

The expected behavior is:

    New ALB
        |
        v
    ExternalDNS
        |
        v
    Route 53
        |
        v
    Updated Alias
        |
        v
    petclinic.website

---

### Rule 7 — Argo Rollouts Should Remain the Traffic Management Layer

The ALB should continue to provide the entry point for application traffic.

Argo Rollouts should control traffic distribution between:

    petclinic-stable

and:

    petclinic-canary

The ALB should not be manually modified to perform canary traffic management.

---

The final validation should demonstrate that the public application identity remains stable even when the underlying infrastructure is replaced.

## Summary

The Petclinic application is exposed using a stable custom domain:

    https://petclinic.website

Route 53 is the authoritative DNS provider.

ExternalDNS automatically synchronizes the Kubernetes Ingress with Route 53.

The AWS Load Balancer Controller creates and manages the AWS Application Load Balancer from the Kubernetes Ingress.

ACM provides the TLS certificate used by the ALB.

HTTP traffic is redirected to HTTPS.

The ALB uses IP targets to route traffic directly to Kubernetes Pods.

Argo Rollouts uses the ALB as the traffic-management layer for progressive delivery between stable and canary services.

Terraform manages the AWS infrastructure.

Kubernetes and Helm manage the application-facing networking configuration.

The key architectural principle is:

    Stable application identity
            |
            v
    Replaceable infrastructure

The application depends on:

    https://petclinic.website

and not on:

    k8s-....elb.amazonaws.com

The ALB can therefore be destroyed and recreated without changing the application's public URL.

ExternalDNS bridges the dynamic Kubernetes/AWS infrastructure with the stable Route 53 DNS name.

ACM provides a reusable TLS identity.

Argo Rollouts provides progressive traffic management.

The resulting architecture is declarative, reproducible and compatible with infrastructure replacement through:

    terraform destroy
    terraform apply
